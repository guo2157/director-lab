# Director-Lab 作品说明

> 从一句剧本到一部短剧：AI Agent 驱动的自托管漫剧生产工作台

## 项目概览

| 项目 | 内容 |
| --- | --- |
| 作品定位 | 自托管、可落地的 AI 漫剧 / 短剧生产工作台 |
| 核心链路 | 剧本 → 解析 → 公共资产 → 分镜图 → 视频 → 配音 → 合成导出 |
| 技术栈 | FastAPI、SQLAlchemy 2.0、Alembic、SQLite（WAL）、Vue 3、TypeScript、ComfyUI |
| 模型能力 | Qwen-Image 2.1（图像）、MiniMax H3（视频）、Qwen3-TTS（配音）、Stable Audio（BGM） |
| 工程规模 | 后端与测试 219 个 Python 文件、约 5.46 万行；前端 74 个文件、约 2.26 万行 |
| 接口与工具 | 227 个 HTTP 操作、28 个 Agent 工具、624 个后端测试用例 |
| 示例成果 | 示例项目《游乐场》：1 集、5 场景、2 角色、4 道具、26 个镜头、约 2 分 17 秒成片 |

Director-Lab 不是一个"输入一句话、等一个视频"的黑盒生成器。它把短剧生产中真正繁琐、重复、需要保持一致性的环节拆开，做成一条可审核、可回滚、可续跑的生产流水线。所有渲染都跑在自建的 ComfyUI 上，不需要云端视频 API，也没有按秒计费。

## 一、核心功能与亮点

### 1. 剧本解析：把剧本变成可执行的结构化数据

**帮助用户完成的任务**

一次解析同时拆出剧集、场景、角色、道具、对白和分镜，并输出镜头级字段：景别、时长、人物动作、站位、道具持有关系、参考图职责和视频提示词。

**原来的方式**

创作者需要手工拆场景、写人物小传、列道具表、按镜头写提示词。一集 26 个镜头通常要维护好几张表，剧本改一处，所有表都要回头同步。

**改进点**

- 解析结果成为下游资产、分镜、配音的唯一输入源，修改剧本后重新解析即可整体刷新。
- 拒绝"残缺落库"：当 LLM 输出被截断时，系统识别截断特征并自动放大 `max_tokens` 重试（放大至 2 倍、上限 32768），同时追加紧凑排版、省略空值、确保 JSON 闭合的输出约束。
- 对不可重试错误（参数缺失、代码错误）快速失败，不做无意义的重复调用。

**结果**：长剧本解析从"大概率失败"变为稳定完成，且保证"要么完整，要么明确报错"。

### 2. 公共资产库与人工审核闸口：解决跨镜头一致性

**帮助用户完成的任务**

解析后先产出角色定妆图、场景基准图、道具锚定图三类公共资产，支持单独 / 批量生成、多参考图、重新生成和人工审核。审核通过后，分镜与视频通过 `@角色名` 自动注入对应参考图槽位，跨镜头复用。

**原来的方式**

每个镜头重新描述一次角色长相，靠"抽卡"碰运气；或者把同一张参考图手动粘贴到每个视频工具里。人物发型、服装、道具一旦漂移，只能整段返工。

**改进点**

- 一致性从"提示词运气"变成"资产引用"，同一角色在 26 个镜头中保持发型、服装、面部特征和道具一致。
- 把人工审核做成后端强制的质量闸口：项目未通过资产审核时，任何入口提交生成都会返回 `409`，从机制上避免"角色图跑偏后一路放大错误、白烧本地 GPU 算力"。
- 提供批量重试、失败对账和断点续跑，避免逐个手动重提。

### 3. 分镜图生成：出图前的三层质检

**帮助用户完成的任务**

基于已审核资产批量生成分镜参考图，每一镜自动绑定角色、场景、道具参考图，支持单镜重新生成且不影响其他镜头。

**原来的方式**

提示词写完直接丢给模型，出图不对再重抽，一张图几分钟起步。

**改进点**

提交前执行三层检查：

1. **编号绑定**：参考图的图序与实际注入槽位对齐，职责描述按真实槽位重写；
2. **确定性门禁**：道具锚定图缺失直接阻断；多角色镜头缺少站位描述判为可修复问题；
3. **LLM 语义复核**：只在确定性检查发现疑点时调用，不无条件重写提示词正文。

**结果**：把"先花 1 秒检查、再花 3 分钟出图"变成默认行为，无效生成显著减少，同时避免 LLM 篡改剧本原文。

### 4. 链式视频生成与任务调度

**帮助用户完成的任务**

视频按镜头序号串行生成，上一镜的尾帧自动提取、命名并绑定为下一镜的首帧参考；任务统一进入队列，支持重试、熔断、断点续跑和多 ComfyUI 实例的加权分发。

**原来的方式**

逐个镜头复制提示词提交，镜与镜之间人物动作和场景接不上，只能靠导演自己记忆；任务失败就从头再来。

**改进点**

- 镜头之间具备物理连续性：尾帧接首帧，动作和场景能够衔接。
- **原子认领**：调度器多线程取任务时使用条件 UPDATE 抢占，避免同一任务被提交两次、产出两个版本。
- **事务纪律**：所有网络、上传、轮询、ffprobe 调用都在数据库事务之外执行，避免调度器轮询不可达的 ComfyUI 时拖垮整个数据库接口。
- **实例池**：心跳探测、自动摘除恢复、least-connections 派发与任务级故障转移。

**三档出片策略（实测数据）**

| 档位 | 单镜时长 | 单镜渲染耗时 | 26 镜串行渲染 |
| --- | --- | --- | --- |
| fast | 5 秒 | 1 分钟以内 | 约 26 分钟以内 |
| std | 5 秒 | 约 2 分 20 秒 | 约 61 分钟 |
| quality | 10 秒 | 约 4 分钟 | 约 104 分钟 |

三档对应独立工作流（`wf_video_h3_ref2va_fast_5s` / `_std_5s` / `_quality_10s`），可以按镜头重要性混用：过场镜头走 fast，关键情绪镜头走 quality。这种"按镜头分配算力"的粒度，是本地渲染相对云端按秒计费最实际的成本优势。

### 5. 提示词编译层：让模型只念该念的台词

**帮助用户完成的任务**

把提示词从"LLM 随手写的散文"改为两层编译：解析阶段只产出结构化事实，生成阶段由编译器按模板渲染，统一处理对白标签化、参考图槽位、画幅参数和负面词。

**原来的方式**

提示词散落在三个地方拼装，同一资产从不同入口生成结果不一致。更麻烦的是，H3 会把提示词里的"台词""第 N 段""无对白"当成要播报的内容，还会自行补充台词、把角色名念出来。

**改进点**

- 对白有唯一来源：结构化 `dialogue_segments`，只保留纯台词并包裹在 `<d>` 标签内。
- 说话类动作描述自动改写为非发声的神情与视线动作，从源头消除发声诱因。
- 含对白镜头在末尾追加显式台词锁定约束：每句仅一次，不得新增、改写、重复或自创台词。
- 无对白镜头改为"环境声"段，只保留声音描述，并追加人声压制规则。
- 画幅、时长等技术规格由工作流的 `width / height / length` 统一注入，提示词中不再出现与项目画幅冲突的硬编码行。

### 6. 合成导出与 AI 导演台

- **合成导出**：FFmpeg 在本地完成镜头拼接、音轨混合、字幕烧录、时长对齐和导出，不占用 ComfyUI 算力；合成与导出拆为两个独立阶段，合成产物可复用。
- **AI 导演台**：注册 28 个工具，支持自然语言操作项目；高风险操作先生成任务卡，经人工确认后才真正执行，执行过程通过事件流回传。
- **刻意的产品选择**：不追求"全自动黑盒"。资产审核、镜头审核和 Agent 高风险操作都保留人工确认，因为一次错误的批量生成，代价是几个小时的真实算力。

### 效率与成本对比

| 传统做法 | 在 Director-Lab 中 |
| --- | --- |
| 手工整理剧本、拆场景、记人物设定 | 一次解析自动产出分集 / 场景 / 角色 / 道具 / 对白 / 分镜 |
| 每个镜头重新描述角色长相 | 角色定妆图作为公共资产，多参考图绑定到每个镜头 |
| 手工挑参考图、写图片提示词 | 分镜规划生成镜头提示词与参考图职责，提交前自动质检 |
| 逐条复制提示词到视频工具 | 分镜看板一键提交，按镜头序号串行生成 |
| 上一镜和下一镜人物、场景接不上 | 尾帧自动提取并绑定为下一镜首帧 |
| 配音、BGM、字幕、拼接各做一遍 | 音频规划 + TTS + FFmpeg 合成统一处理 |
| 生成失败从头再来 | 任务队列、重试熔断、版本化重生成、断点续跑 |

## 二、TRAE 在开发过程中的具体帮助

分工方式：**我负责定义问题、判断取舍、制定验收标准；TRAE 负责跨文件定位、批量改造、补测试和回归验证。**

### 案例 1：把散落三处的提示词拼装收敛成一层编译器

**需要解决的问题**

提示词构建分散在资产提示词构造器、生成端点和 Agent 工具兜底分支三处。同一角色从不同入口生成，提示词不一致；参考图缺失、审核未过、槽位超限都要等提交后才暴露，等于白烧 GPU。

**我的判断与选择**

不在每个入口逐个打补丁，而是收敛成一个只接受四类输入的纯函数层：结构化事实、模板、已审核资产、工作流真实能力。输出必须可校验、可追溯；编译期不通过，就不允许写入生成参数。

**TRAE 具体协助完成的**

- 新增 `backend/app/services/prompt_compiler.py`（1,939 行），实现 `CompiledPrompt` 结构与 `validate_compilation` 严格校验；
- 把生成端点和 Agent 工具统一接入 `_compile_asset_prompt` / `_compile_shot_prompt` 两个入口，删除旧的兜底分支；
- 新增测试，把"文档模板与运行时常量逐字符一致"固化下来，避免规范漂移。

**最终体现**

任一资产、任一入口，提示词都可追溯（写入 `job.input_snapshot.prompt_compilation`），一致性问题在提交前就会报错。

### 案例 2：调度器重复认领导致同一镜头生成两个版本

**需要解决的问题**

用户反馈某个镜头重新生成后出现多个版本号，ComfyUI 中能看到同一任务被提交了两次。

**我的判断与选择**

这不是偶发问题，而是"取任务"与"置状态"之间缺少原子性：工作线程还没把状态改成 `running` 的窗口期，同一任务会被再次取到。解决方案必须是数据库层的条件更新，而不是在应用层加锁。

**TRAE 具体协助完成的**

- 将状态置位改为条件 UPDATE 抢占，抢不到立即返回，不重复提交；
- 补齐取任务与占位之间的事务边界；
- 补充并发场景的回归测试。

**最终体现**

重复提交消失，重新生成稳定只产出一个有效版本，并顺带把单版本机制在前后端全部打通。

### 案例 3：解析输出截断，整集解析失败

**需要解决的问题**

剧本较长时 LLM 返回被截断，JSON 解析失败，表现为解析页长时间无结果或直接报错。

**我的判断与选择**

绝不能接受残缺结果写入数据库，但也不应该让用户手动重试。截断是可识别、可自动补救的，应该在执行器层面闭环。

**TRAE 具体协助完成的**

- 在 LLM 调用层增加截断特征识别与单次 `max_tokens` 覆盖；
- 在执行器中实现自动重试：重试时将 `max_tokens` 放大至原配置的 2 倍（上限 32768），并追加"紧凑排版、省略空值、确保 JSON 闭合"的输出约束；
- 将参数缺失、代码错误等不可重试错误设为快速失败。

**最终体现**

长剧本解析从"大概率失败"变为"稳定完成"，重试逻辑也不再对无意义错误做无效重试。

### 案例 4：替换分镜图后页面不更新

**需要解决的问题**

用户在分镜图页面替换图片，后端返回成功，但页面仍显示旧图。

**我的判断与选择**

问题不在前端渲染，而在资产原地覆盖时 URL 没有变化，浏览器直接命中缓存。这也和公共资产页已有的处理方式不一致，应该在资产序列化层统一解决。

**TRAE 具体协助完成的**

- 在资产序列化层为图片 URL 统一追加基于 `updated_at` 的时间戳参数；
- 覆盖 `shots.py` 与 `assets.py` 两条返回链路，替换接口同步返回新 URL。

**最终体现**

替换即生效，用户不需要手动清缓存。这类"看起来像前端 bug、实际是缓存语义"的问题，TRAE 的全仓库检索能力帮助减少了大量猜测。

### 案例 5：一键部署脚本与模型管理

**需要解决的问题**

自托管方案的门槛在环境：ComfyUI 安装、模型下载与校验、显存与加速配置，手动操作容易出错，且模型体积大（H3 与 Qwen 两组约 66 GiB），重复下载成本高。

**我的判断与选择**

把部署做成可重复执行的幂等脚本，而不是一份 README 步骤清单。已完整下载的模型必须跳过校验，避免重复拉取。

**TRAE 具体协助完成的**

- 编写 `autodl_comfyui_qwen21_h3_setup.py` 与 `cloudstudio_comfyui_qwen21_h3_setup.py`，支持 `all / download / status / plan / log` 子命令；
- 增加模型完整性校验，跳过已下载文件；
- 提供 `h3vram`（低显存）与 `h3speed`（出片提速）配置组。

**最终体现**

新环境从零到可出片只需执行一条命令，部署过程可复现、可排查。

## 三、印象最深的经历：和"会自己加戏的模型"周旋

如果只讲一段经历，我会讲对白失控的那几天。

### 背景与处境

项目已经能跑通全链路：资产、分镜、视频都出来了，成片也导得出来。但试看时发现一个很刺眼的问题：**角色说了台词里根本没有的话。** 有时是把自己的名字念了一遍，有时是凭空多出一段抱怨，有时是把提示词里的"无对白"三个字念了出来。

对一个短剧产品来说，这不是"效果不好"，而是**不可用**。台词是剧本的核心，念错就等于废片。

更难的是，这类问题没有标准答案，也不能靠读代码定位。代码逻辑完全正确，它只是把提示词原样发给了模型。我一开始的直觉是换模型参数、加负面词、调温度，试下来收效很小，甚至时好时坏。

### 最难的一环：承认自己的假设错了

我原本以为"模型不听话"。后来把同一镜头的输入快照和输出逐段对照，才发现真正的原因：**是提示词在教它说话。**

动作段里写着"他抱怨了一句""她开口问"，对白行里写着角色名。模型非常"听话"地把这些都念了出来。问题不在模型，而在我的提示词里混入了发声指令。

这一环最难，因为它要求我放弃已经投入的调试方向，承认问题出在自己设计的东西上。

### 采取的行动

我停止了"调参数"这条路，转而做三件事：

1. **建立唯一事实源**：对白只从结构化 `dialogue_segments` 重建，只保留纯台词并包裹在 `<d>` 标签内，其余一律不进入语音内容；
2. **把说话类动作改写为非发声描述**：把"抱怨""开口""问话"改成可观察的神情、视线、手部动作，从源头消除发声诱因；
3. **加显式锁定约束**：含对白镜头在末尾明确约束"只播报 `<d>` 内的台词，每句仅一次，不得新增、改写、重复"。

同时，我把这套规则做成幂等函数，在"解析写入数据库前"和"生成提交前"两个环节统一执行。这只是一个函数，放在两个入口，是为了保证不管从哪个入口进来，下发给模型的都是同一份规范化结果。

### 结果

重新生成后，对白严格落在剧本台词上，角色名不再被念出来，无对白镜头只剩环境声。

更重要的是，这次之后我把"提示词不当"当成一类**可系统性防御的缺陷**，而不是运气问题。后续又沉淀出一批规则：画幅参数统一注入、清理 `<d>` 标签后的语气描述、参考图职责按实际槽位重写、无对白镜头改写为环境声——全部落在编译器里，而不是靠人记住。

### 这件事反映的思考方式

我比较相信一个判断顺序：**先分清是模型能力问题，还是输入质量问题。** 前者要换方案，后者要改工程。

很多时候我们抱怨 AI 不听话，其实是把互相冲突的指令一起塞给了它。这个判断方式后来也用在分镜图质检上：先做确定性的、便宜的结构检查，只有发现疑点才调用大模型复核。**能用规则解决的，就不要交给概率。**

## 附录 B：实测数据与测算口径

### B.1 单镜渲染耗时（实测）

| 档位 | 单镜时长 | 单镜渲染耗时 | 26 镜串行渲染 |
| --- | --- | --- | --- |

| std | 5 秒 | 约 2 分 20 秒 | 约 61 分钟 |
| quality | 10 秒 | 约 4 分钟 | 约 104 分钟 |

### B.2 耗时结构

在 std 档下，26 个镜头的视频渲染约 61 分钟，是整条链路里最耗时的部分。解析、资产图、分镜图、合成由任务队列自动串行，人工只需要在资产审核、分镜图确认、成片验收三个节点介入。

### B.3 人工投入对比

| 环节 | 传统流程 | Director-Lab |
| --- | --- | --- |
| 镜头拆解与提示词 | 逐镜手工撰写，维护多张表格 | 解析一次自动产出，质检通过后才提交 |

测算口径：传统流程的单镜人工投入主要来自镜头拆解、提示词撰写、多工具切换与抽卡返工、下载命名与手动拼接，可按"每镜实际耗时 × 26"估算；Director-Lab 侧可核算的纯渲染时间为 61 分钟（std 档），人工投入集中在审核与局部重做。提交前建议填入本次实际操作的总时长。
